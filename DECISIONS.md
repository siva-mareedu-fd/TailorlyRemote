# Decisions

Decisions made while building, with the reason. Proposed changes to `docs/` are listed at the end and are not
applied to the docs until the owner agrees.

| Date | Decision | Reason |
|---|---|---|
| 2026-10-25 | Target **.NET 10** (current LTS), SDK pinned in `global.json` (`10.0.100`, roll forward to the latest feature band). | CLAUDE.md: latest .NET LTS. |
| 2026-10-25 | Node **24 LTS** locally and in CI and Docker; `engines` requires ≥ 22.12. **TypeScript pinned to 5.9**. | Vite 8 needs Node ≥ 20.19/22.12. TypeScript 7 (native) and 6 are not yet accepted by `typescript-eslint` / `openapi-typescript` peer ranges. |
| 2026-10-25 | Tests use **xUnit v3 on Microsoft.Testing.Platform** (`global.json` `test.runner`), and **FluentAssertions pinned to 7.x**. | xUnit v3 is current; .NET 10 `dotnet test` requires the MTP opt-in. FluentAssertions 8 changed to a commercial licence; 7.x is Apache-2.0. |
| 2026-10-25 | `Newtonsoft.Json` pinned to 13.0.4 via central transitive pinning. | `Hangfire.Core` 1.8 references 11.0.1, which has a known high-severity advisory (GHSA-5crp-9r3c-p9vr); NuGet audit + warnings-as-errors fails the build otherwise. |
| 2026-10-25 | Hangfire dashboard (`/admin/jobs`) gets a **relaxed CSP** (`'unsafe-inline'` for scripts and styles). Every other path keeps `default-src 'self'` with no inline code. | The dashboard ships inline scripts/styles; it is Admin-only (endpoint policy + dashboard filter). |
| 2026-10-25 | **Migrations in Compose run as a one-shot `migrate` service** (`Tailorly.App --migrate`) that `app` waits for (`service_completed_successfully`). The app never migrates itself. `--migrate` also installs the Hangfire schema (`PrepareSchemaIfNecessary=false` at runtime). | Satisfies "migrations via `--migrate`, never on app startup" (SDD §12.5) while keeping `docker compose up` one command. The deploy script in M6 can still run it explicitly first. |
| 2026-10-25 | Identity table and index names are **forced to snake_case** in `AppDbContext` (`asp_net_users`, `ix_asp_net_users_email`, …). | Identity sets explicit PascalCase names that `EFCore.NamingConventions` does not override; DatabaseDesign §1 requires `asp_net_users`. |
| 2026-10-25 | Cookies: auth `__Host-tailorly`, antiforgery `__Host-tailorly-af` (HttpOnly), readable `XSRF-TOKEN`; all `Secure`. Integration tests call the TestServer over `https://localhost` instead of relaxing cookie settings. Local `dotnet run` uses the HTTPS dev profile (`https://localhost:7080`). | Same cookie behaviour in tests, dev and production. Antiforgery refuses non-HTTPS requests when the cookie is `Secure`. |
| 2026-10-25 | The app trusts `X-Forwarded-*` from any proxy (`KnownIPNetworks` cleared). | Only Caddy can reach the app (internal Docker network; the app publishes no ports). Needed so the app sees `https`. |
| 2026-10-25 | **Data Protection keys** persisted to `/data/keys` (volume `dpkeys`) when `DataProtection__KeysPath` is set. Keys are stored unencrypted at rest (the app logs a warning about it). | Otherwise every restart signs users out and invalidates CSRF tokens. Key encryption joins the Phase 2 encryption epic (PRD D11). |
| 2026-10-25 | **PII log scrubbing** is two layers: a destructuring policy for `{@Obj}` and an enricher that removes blocked properties from every event (template properties, nested structures, dictionaries). Names ending in `email` (e.g. `NotificationEmail`) are blocked too. JSON output writes the message template, never the rendered message. | A destructuring policy alone does not cover `{Email}` template properties or framework events. Blocking `*email` is stricter than SDD §14.3 and safer. |
| 2026-10-25 | Correlation id: client `X-Correlation-Id` accepted only if ≤ 64 chars of `[A-Za-z0-9._-]`, otherwise a new id; it is the request `TraceIdentifier`, so it is the `traceId` in every problem body; carried into Hangfire jobs. | Prevents log injection; one id end to end. |
| 2026-10-25 | Rate-limit buckets from ApiDesign §6 are all registered, with limits in `RateLimits:{bucket}`. On 429 the response carries `RateLimit-Limit`, `RateLimit-Remaining: 0`, `Retry-After`. Per-**email** partitions for `auth-register`/`auth-mail` are added with those endpoints in M1. | ASP.NET's limiter does not expose remaining permits per request; the doc only requires the headers on 429. Email partitions need the request body. |
| 2026-10-25 | Problem `type` URIs use `https://tailorly.example/errors/{code}` as in ApiDesign §1.1. | Matches the doc; replace the host when a domain exists. |
| 2026-10-25 | Feature flags use the DB keys from DatabaseDesign §5 (`signup.require_invite_code`), not the PRD's `Signup:RequireInviteCode`. | The DB design is authoritative for schema and seed data. |
| 2026-10-25 | SPA routes follow the design prototype (`/shortlist`, `/tracker`, `/add-job`, `/resume`, `/preferences`, `/usage`, `/account`, `/admin`, `/onboarding`, `/signin`, `/signup`, `/jobs/:id`). | PRD §12 lists Dashboard and Jobs list separately; the final design merges them into the Shortlist. The design is the visual reference. |
| 2026-10-25 | Fonts are **self-hosted** via `@fontsource` (IBM Plex Sans/Mono), not Google Fonts. | The CSP is `font-src 'self'`; no third-party requests. |
| 2026-10-25 | Tailwind theme maps the prototype tokens 1:1 (`bg-surface`, `text-muted`, `rounded-card`, `shell:` breakpoint at 861 px…). shadcn/ui names (`primary`, `background`, `popover`, …) are aliased to the same tokens; **`accent` keeps the design meaning (brand green)**, not shadcn's hover colour, so generated shadcn components must be adjusted when added. | Fidelity to the design; one palette. |
| 2026-10-25 | Theme defaults to **light** with a stored choice winning (as the prototype does); the `prefers-color-scheme` token block is kept for completeness. The theme is applied in `main.tsx` before render. | Matches the prototype; no inline script allowed by the CSP. |
| 2026-10-25 | The sidebar shows the Admin section for everyone and budget bars as "—" in M0. | `/me` (roles) and `/usage` arrive in M1; no fake numbers. |
| 2026-10-25 | `Ai:Provider` accepts only `Fake` in M0 (startup fails otherwise). | The Anthropic provider (official SDK vs thin HttpClient) is chosen and built in M1. |
| 2026-10-25 | `IFxRateProvider` has a config-driven `StaticFxRateProvider` placeholder. | The daily-cached public provider is needed in M3 (salary display). |
| 2026-10-25 | Dependabot enabled for NuGet, npm, Docker and Actions. | SDD §14.2 supply-chain control. |
| 2026-10-25 | M0 docs-conformance audit. `.gitignore`/`.dockerignore` storage rules anchored to the runtime folders (`/storage/`, `/src/Tailorly.App/storage/`). | The unanchored `storage/` also matched `Infrastructure/Storage/` (Git on Windows ignores case), so `LocalFileStore.cs` was never committed and a clean checkout did not build. |
| 2026-10-25 | A wrong HTTP method on an existing route returns **404 `NOT_FOUND`** (not 405); the `Allow` header is dropped. | ApiDesign §1.2 does not list 405. Before, the body said `status: 405` with `code: NOT_FOUND`. |
| 2026-10-25 | A transient database failure (`NpgsqlException.IsTransient`, raw or wrapped once) returns **503 `SERVICE_UNAVAILABLE`** instead of 500. | SDD §15.1: "DB unavailable → API returns 503". The code is not in the catalogue yet (proposal 6). |
| 2026-10-25 | OpenAPI declares the §1.1 error body as schema `ApiProblem` and adds it as the `default` response of every operation (`ProblemOpenApiTransformer`). The SPA uses the generated type. | The contract snapshot had no error shape, so the SPA kept a hand-written copy that could drift. |
| 2026-10-25 | `/healthz` and `/readyz` stay **out of the OpenAPI document**. | They are outside `/api/v1`, take no input, and are called by Compose/Caddy/CI, not by the SPA. ApiDesign §4.1 lists them; their contract is the status code only. |
| 2026-10-25 | The M0 seed covers `ai_task_config` and `feature_flags` only. `job_sources` + `source_health` seed rows (DatabaseDesign §5) arrive with their tables in M2. | M0 builds the account tables only (§3.1); the other tables do not exist yet. |
| 2026-10-25 | **M1** `IModelProvider` uses the **official Anthropic .NET SDK** (`Anthropic` 13.3.0, published by Anthropic, stable). Retries for this client are the SDK's own (408/409/429/5xx and connection errors, `Anthropic:MaxRetries=3`), not a Polly pipeline. | CLAUDE.md: use the official SDK when a stable release exists. Two retry layers would multiply attempts. |
| 2026-10-25 | **No sampling parameters are sent.** `ai_task_config.temperature` stays in the schema and seed but is not used. | SDK 13.x speaks API version `2026-10-21`, which rejects `temperature`/`top_p`/`top_k` with a 400 on every model. |
| 2026-10-25 | Replies use **structured outputs** (`output_config.format` = the task's JSON schema) **and** are validated locally with **NJsonSchema** (MIT) plus a domain validator, with one repair turn (user → invalid reply → "fix these problems") and then `AI_INVALID_OUTPUT`. The schema sent to the model drops keywords structured outputs does not support (lengths, ranges, array sizes); those are enforced locally. | Structured outputs make invalid JSON rare; local validation keeps the guarantee independent of the provider. JsonSchema.Net 8+ ships under a non-OSI licence, so NJsonSchema. |
| 2026-10-25 | Reasoning **effort is configuration** (`Ai:Effort`, default `low`; per task `Ai:Tasks:{task}:Effort`), not a column. | Current models think adaptively by default and Sonnet 5.5 cannot turn thinking off; extraction needs little. A column would change the schema (proposal 12). |
| 2026-10-25 | No server-side model fallback (`fallbacks`) is requested. A refusal ends the task as `AI_INVALID_OUTPUT` without a repair turn. | SDD §9.3: no automatic model fallback. |
| 2026-10-25 | Prompts are `Ai/Prompts/{task}.md` with `version:` front matter; schemas `Ai/Schemas/{task}.schema.json`; both embedded. Résumé text goes in `<resume_data>` delimiters; delimiter-like text inside is neutralised. Prompt bytes use `\n` on every OS. | PRD Appendix C; prompt caching needs stable bytes. |
| 2026-10-25 | Parse failure codes on the résumé row: `BUDGET_EXCEEDED`, `AI_UNAVAILABLE`, `AI_INVALID_OUTPUT`, `UNSUPPORTED_FILE_TYPE` (OpenXML could not read it, or it has no text), `TIMEOUT` (sweep). | `AI_INVALID_OUTPUT` is new (proposal 11); the rest are catalogue codes. |
| 2026-10-25 | `ParseResume` retries transient AI failures **twice, after 1 and 5 minutes** (not 5/15/45). | The stuck-work sweep fails résumés 30 min after `created_at` (DatabaseDesign §7); 5+15+45 min would always lose to it (proposal 13). |
| 2026-10-25 | Extra partial unique index `ux_resumes_parse_inflight (user_id) WHERE parse_status IN ('queued','running')`: one parse in flight per user; a repeated upload while parsing returns **200** with that résumé. | ApiDesign §1 "duplicate submissions"; CLAUDE.md: in-flight duplicates are prevented by partial unique indexes (proposal 14). |
| 2026-10-25 | A new version **becomes active automatically** when its parse is ready (previous one deactivated). | ApiDesign §4.4 says so; the prototype's "Make active" button after parsing is not followed (proposal 17). Older versions can still be activated. |
| 2026-10-25 | Version numbers are `max(version)+1` of the user's existing résumés, so deleting the latest version lets its number be reused. | No counter column in the DDL. M3 keys scores on `resume_version` and must not see reuse (proposal 15). |
| 2026-10-25 | `format_findings` stores **no text**: `headerFooterText` is a boolean, plus `headerFooterContact`, `pageEstimate`, `complexParagraphs`, `schemaVersion`. The API's `formatFindings` carries these extra fields (additive). | Contact details are PII; the boolean is what the format-health score needs (proposal 16). |
| 2026-10-25 | Extraction heuristics, tuned on synthetic fixtures and two local résumés (counts only, never committed): headings are detected in layout tables too; an unknown heading-styled line inside Summary/Experience/Projects/Skills is a locked sub-heading that keeps the section; bookmarks other than `_GoBack` make a paragraph complex; table cells may be editable (flag `InTable`). | SDD §10.1 lock rules; T3 (layouts vary). The two local résumés went from 0 and 87 to 90 and 87 editable paragraphs with all sections found. |
| 2026-10-25 | Upload safety extras: write protection and enforced document protection count as **password-protected**; the main part may be declared by a `Default` content type (as the OpenXML SDK writes it); any failure to read the zip is `UNSUPPORTED_FILE_TYPE` ("corrupt"). Decompressed bytes are counted while reading, never trusted from headers. | SDD §10.5 asks to reject password-protected files; real files use both OPC forms. |
| 2026-10-25 | Password policy: **10+ characters and 4 distinct characters**, no composition rules. | The sign-up design says "Use 10 or more characters. A passphrase works well."; Identity's defaults would demand a digit and an uppercase letter. NIST 800-63B. |
| 2026-10-25 | Link lifetimes: verification **24 h** (PRD F1), password reset **1 h** (own token provider), account deletion **1 h** (time-limited Data Protection token bound to the security stamp, purpose `Tailorly.AccountDeletion.v1`). | PRD F1 and SDD §7.5; the reset lifetime is not in the docs, 1 h is the common safe default. |
| 2026-10-25 | Account mail goes through `AccountEmailJob.SendAsync(kind, userId)` (Hangfire, 3 retries at 1/5/30 min). Job arguments are only the kind and the id; **tokens and links are minted when the job runs**, so no token is stored in the job queue. Links use `App:PublicBaseUrl`, never request headers. | SDD §11.5; keeps secrets out of the hangfire schema; avoids host-header injection. |
| 2026-10-25 | `POST /auth/register` is uniform: an existing email gets 201 with a random `userId` and the owner gets an "already have an account" email. Password policy, consent and invite validity are checked **before** the account lookup, and the invite is consumed in the same transaction as the user. | ApiDesign §4.2; otherwise a weak password or bad invite would answer differently for existing emails. |
| 2026-10-25 | Per-email/per-user limits (`auth-register-email` 3/h, `auth-mail-email` 5/h, `auth-resend-user` 3/h) are in-memory partitioned limiters keyed by SHA-256 of the address, configurable like the other buckets. `ApiException` carries response headers (`Retry-After`, `RateLimit-*`) because the exception handler clears the response before writing the problem. | ApiDesign §6; completes the M0 note. Found by the lockout test. |
| 2026-10-25 | Policies: `UserAny` (`user*`: signed in, account active), `User` (+ verified email), `Admin` (+ verified, Admin role). Failures answer `ACCOUNT_DISABLED` / `EMAIL_NOT_VERIFIED` through an `IAuthorizationMiddlewareResultHandler`; the account flags are read once per request. | ApiDesign §5 and §7 "Account state". |
| 2026-10-25 | `consent_ip_hash` = HMAC-SHA256(client IP, `Security__IpHashKey`). Without the key the app logs a warning and uses a fixed key. | Plain SHA-256 of an IPv4 address is reversible by brute force. |
| 2026-10-25 | Deletion log: append-only file `/data/deletion-log/deletions.log` on its own volume (`deletionlog`), one line `{userId},{UTC time}`, written when the deletion is **confirmed**. `backup.sh` copies it; shipping it off-VM is part of the M6 backup work. | SDD §7.5 step 2 and §13.4. |
| 2026-10-25 | Purge: enqueued right after confirmation and also hourly (`PurgeDeletedAccounts`, recurring). Order: delete files (keys, then the `{userId}/` prefix) → `audit_log` row `account.purged` (entity id only, file count) → delete the Identity user (cascade). `account.delete.requested`/`confirmed` are audited too. | DatabaseDesign §8; idempotent and resumable. |
| 2026-10-25 | The SPA's `/confirm-deletion` page needs an explicit click; it never confirms on page load. | Mail scanners and link previews open URLs; a GET-triggered deletion would be unsafe. |
| 2026-10-25 | Request logging moved **outside** the exception handler. | Inside it, every expected 4xx `ApiException` was logged as a 500 error with a stack trace. |
| 2026-10-25 | Tests replace Hangfire's `IBackgroundJobClient` with an inline recorder (`RunAllAsync`), capture email, and capture logs through `ReadFrom.Services` (a DI-registered Serilog sink). The isolation test **discovers every `/api/v1` route** and fails on any route that is not public, an own-data action, a GET, or covered by an id resolver. | ApiDesign §12; CLAUDE.md "make it automatically cover new routes". |
| 2026-10-25 | Frontend M1: onboarding builds steps 1–2 and **finishes on the Résumé page** (preferences and schedule arrive with M2); the Usage page shows the two budgets only (per-task and per-day history in M5) and **omits the prototype's model chips** ("Haiku"/"Sonnet"); the Résumé page shows format findings without the numeric format-health score (M4); `/privacy` and `/terms` hold placeholder text pending legal review. The sidebar's Admin section is now shown only to the Admin role and its budget bars come from `GET /usage` (supersedes the M0 rows above). | Milestone scope; model names live only in `ai_task_config`. |
| 2026-10-25 | `PUT /me` lets the user change the notification email without verifying it. | Nothing is sent to it before the digest (M3); proposal 18. |
| 2026-10-25 | **Proposals 11–18 approved by the owner.** Options chosen: 12 keep `temperature` as an informational column (no drop; an `effort` column is considered with the next AI task that needs a non-default effort; until then `Ai:Tasks:{task}:Effort`); 13 the shorter 1/5-minute retries as built; 15 a monotonic counter `user_profiles.resume_versions_issued` (migration `M1ResumeVersionCounter`, backfilled from the current max version), so score keys stay `(user_id, job_id, resume_version)`; 18 **yes**: a changed notification email must be verified before any digest is sent to it, to be built with the digest in M3 (until then the email is stored only). ## Proposed doc changes (not applied)

Status: 11–18 approved on 2026-10-25 (see the decision row above); the doc text is not yet updated.

1. **PRD §7.1b** "Configuration" block repeats five lines (`Sources__Jobicy__PollMinutes` … `Fetch__FirstRunBackfillDays`). Remove the duplicates.
2. **PRD §4 F1 / Appendix A** name the invite-code flag `Signup:RequireInviteCode`; DatabaseDesign seeds `signup.require_invite_code` in `feature_flags`. Propose: the PRD refers to the DB flag, and the config key is only the default.
3. **PRD §12** lists Dashboard and Jobs list as separate pages; the final design merges them into **Shortlist**. Propose: update §12 to the design's screen list.
4. **SDD §14.4** says CSP has "no inline scripts" without exception. Propose: note the Admin-only Hangfire dashboard exception.
5. **DatabaseDesign / SDD §16.3**: document where Data Protection keys live (volume `dpkeys`) and that they must be backed up with the documents volume.
6. **ApiDesign §10**: add `SERVICE_UNAVAILABLE` (503): "A dependency other than the AI provider (the database) is unavailable; retry later." §1.2 already lists 503 as "dependency unavailable", but the only 503 code is `AI_UNAVAILABLE`.
7. **ApiDesign §10**: say that `FILE_TOO_LARGE` (413) also covers any request body over its limit (1 MB JSON, §7), and `UNSUPPORTED_FILE_TYPE` (415) any unsupported `Content-Type`. These are the only 413/415 codes and the platform returns them for non-upload requests too.
8. **ApiDesign §1.2**: state that a wrong method on an existing path returns `404 NOT_FOUND` (no 405).
9. **DatabaseDesign §3.1 / §3.7**: add the two foreign-key indexes EF creates by convention, `ix_audit_log_actor_user_id` and `ix_ai_task_config_updated_by`. The first is needed anyway: deleting a user runs `ON DELETE SET NULL` on `audit_log`, which would otherwise scan the whole table. Also note that the Identity tables keep Identity's own column types (`varchar(256)` for names/emails), an exception to the "`text`, no length limits" rule in §1.
10. **SDD §13.2 / §14.2** ("pinned base images"): the dev-only Mailpit service uses `axllent/mailpit:latest`, and Gotenberg is pinned only to major `8`. Propose: pin both to exact versions when Gotenberg is enabled (M7, PDF), and let Dependabot bump them.
11. **ApiDesign §10**: add `AI_INVALID_OUTPUT` (resource error code): "The AI reply failed validation after one repair; try again." Today the catalogue has no code for this outcome.
12. **DatabaseDesign §3.7 / §5, PRD §6.1, SDD §9.1**: API version `2026-10-21` removed sampling parameters, so `ai_task_config.temperature` has no effect. Propose: mark it informational (or drop it in a later contract migration) and consider an `effort` column (`low|medium|high|max`) so effort is routed per task from the database like the model.
13. **SDD §9.1 / §11.2, DatabaseDesign §7**: the 5/15/45-minute re-queue schedule cannot complete before the 30-minute stuck-work sweep, which keys résumés on `created_at`. Propose: either shorter retries (as built: 1 and 5 min) or an `updated_at` on `resumes` and a sweep on it.
14. **DatabaseDesign §3.2 / §6**: add `ux_resumes_parse_inflight` (one parse in flight per user).
15. **DatabaseDesign §3.2**: version numbers can be reused after the latest version is deleted, while `user_job_scores` is unique on `(user_id, job_id, resume_version)` (M3). Propose: a monotonic per-user counter (e.g. `user_profiles.resume_versions_issued`) or keying scores on `resume_id`.
16. **DatabaseDesign §4** (`resumes.format_findings`): `headerFooterText` is a boolean (no résumé text stored); add `headerFooterContact`, `pageEstimate`, `complexParagraphs`, `schemaVersion`. ApiDesign §4.4 `Resume.formatFindings` gains the same fields.
17. **Design prototype (#resume) vs ApiDesign §4.4**: the prototype asks the user to "Make active" after a parse; the API activates automatically. Propose: keep the API rule and change the prototype copy to "…is now active".
18. **PRD F1 / ApiDesign §4.3**: decide whether a changed `notificationEmail` must be verified before digests are sent to it (M3).
